# AI 客服训练公司技术栈迁移设计

> 历史设计记录，不是当前运行说明。当前技术基准见[项目技术栈模板](../../../PROJECT_TECH_STACK.md)，当前状态见[统一验收标准](../../../ACCEPTANCE.md)。

日期：2026-08-05

状态：已完成方案讨论，待书面规格审阅

## 1. 目的与基准

本项目将从现有 Next.js 全栈应用迁移为公司统一的前后端分离技术架构。仓库内的 [`docs/PROJECT_TECH_STACK.md`](../../../PROJECT_TECH_STACK.md) 是本次迁移的权威技术基准，约束目标框架、基础依赖、目录结构、开发端口和服务器脚本风格。该文件保持原文，不在实施中随意改写；如公司以后发布新版模板，应先单独评审模板差异，再调整本设计。

迁移后的目标是完整保留当前学员端、管理端、知识与题库发布、AI 情景训练、报告、权限和历史数据，不借技术迁移删除业务能力。旧系统在新系统功能与数据验收完成前继续运行。

## 2. 已确认的技术决策

| 范围 | 决策 |
| --- | --- |
| 后端 | Python 3.12+、FastAPI 0.115.12、Uvicorn 0.34.2、SQLAlchemy 2.0.27、Pydantic 2.10.6 |
| 数据库 | MySQL + PyMySQL，字符集为 `utf8mb4` |
| 前端 | Vue 3、Vite 5、Vue Router 4、Pinia 3、Axios 1.7 |
| 身份认证 | 飞书 OAuth 登录；`union_id` 为企业身份键，同时保存当前应用 `open_id`；后端签发 JWT |
| AI | 豆包 Ark 为首个正式 Provider |
| 部署 | 公司 Linux 服务器；Nginx 托管前端并代理 API；Uvicorn 由 systemd 管理 |
| 切换 | 允许短维护窗口；不建设旧、新系统双写 |
| 数据 | 账号、角色、内容版本、题库、场景、会话、消息、报告、任务和审核记录全部迁移 |
| 实战记录 | 日期时间线 + 同场景折叠；最新会话直接操作，旧记录按需展开 |

公司模板未覆盖但生产迁移必需的能力可以补充：Alembic 管理数据库版本，pytest、Vitest/Vue Test Utils 和 Playwright 维持自动化验收。这些补充不替换模板指定的核心技术。

## 3. 目标架构

### 3.1 仓库布局

目标仓库包含两个独立应用：

```text
backend/
├── main.py
├── requirements.txt
├── alembic.ini
├── config/
│   └── settings.py
├── alembic/
├── app/
│   ├── api/
│   ├── core/
│   ├── models/
│   ├── schemas/
│   ├── services/
│   ├── utils/
│   └── prompts/
└── tests/

frontend/
├── package.json
├── vite.config.js
├── src/
│   ├── main.js
│   ├── App.vue
│   ├── router/
│   ├── stores/
│   ├── api/
│   ├── views/
│   └── components/
└── tests/
```

迁移期间不移动现有 Next.js 文件。新目录与旧系统并存，避免影响线上服务和既有验证命令。最终切换成功后为旧系统创建 Git 标签，再从主线删除 Next.js、React、Auth.js、Drizzle、Neon 和 Vercel 专属实现。

### 3.2 后端边界

- `api/`：路由、请求依赖、输入校验、权限门禁和 HTTP/SSE 响应转换。
- `services/`：认证、知识、题库、实战、任务、审核等业务编排，不依赖 FastAPI 请求对象。
- `models/`：SQLAlchemy 持久化模型。
- `schemas/`：Pydantic 请求、响应和领域传输模型。
- `core/`：数据库会话、JWT、异常、日志、请求 ID 和依赖注入。
- `utils/`：飞书、Ark、文件解析等外部客户端与适配器。
- `prompts/`：版本化的对话、风险识别和评测提示词。

页面不能直接访问数据库或 Ark。业务服务通过稳定接口使用持久化和模型 Provider，确保测试替身及以后更换供应商时不影响 API。

### 3.3 前端边界

- `views/` 负责路由页面和页面级数据装配。
- `components/` 负责可复用展示与交互组件。
- `stores/` 仅保存跨页面状态，包括当前用户、权限和必要的训练草稿。
- `api/` 封装 Axios 客户端、领域 API 和统一错误处理。
- Vue Router 继续保留现有主要业务路径，减少用户习惯和验收脚本变化。

普通请求使用 Axios。报告生成是长连接响应，使用浏览器原生 SSE 能力；身份 Cookie 会随同源请求发送。

## 4. API 与身份设计

### 4.1 通用约定

所有新接口位于 `/api/v1`。成功响应使用明确的资源结构；错误统一为：

```json
{
  "code": "SCENARIO_SESSION_NOT_FOUND",
  "message": "实战会话不存在。",
  "details": null,
  "request_id": "01J..."
}
```

`code` 供前端稳定分支判断，`message` 为可展示中文信息，`details` 只包含安全的字段级错误，`request_id` 用于日志关联。401、403、404、409、422 和上游服务错误分别映射，不能把堆栈或密钥返回浏览器。

### 4.2 飞书登录

1. 前端访问后端飞书登录入口。
2. 后端生成带状态校验的飞书授权地址并重定向。
3. 回调使用授权码取得飞书用户资料，读取验证邮箱、`union_id` 和 `open_id`。
4. 首次登录时，以验证邮箱精确匹配唯一旧账号；成功后永久绑定 `union_id`。
5. 无匹配或多匹配时拒绝自动授予权限，由管理员完成映射。
6. 后端签发短时访问 JWT 和可轮换刷新 JWT，使用 `Secure`、`HttpOnly`、`SameSite=Lax` Cookie；Pinia 只保存当前用户视图，不保存令牌。

旧 Credentials 密码哈希不进入新认证体系。用户 ID、角色、任务和训练历史归属保持不变。管理员权限只来自迁移后的服务端角色数据。

### 4.3 实战记录接口

```text
GET /api/v1/me/scenario-history
  query: status=all|active|completed, cursor, limit=20

GET /api/v1/me/scenario-history/{scenario_id}/sessions
  query: status=all|active|completed, cursor, limit=10
```

列表接口按稳定 `scenarioId` 聚合，返回：场景 ID、标题、分类、总训练次数、进行中数量、已完成数量、最新会话摘要、最新活动时间和下一页游标。组按最新活动时间倒序排列，再由前端按 Asia/Shanghai 日期渲染时间线。

展开接口返回该场景的会话摘要并按更新时间倒序排列。默认折叠旧记录；组头直接展示最新会话。若最新会话进行中，显示“继续最新”；若已完成，显示分数、结果和“查看报告”。多个进行中会话存在时，其余会话在展开区域内可继续。组内超过十条时显示“加载更多”。

### 4.4 Ark Provider

Ark 适配层暴露三个业务接口：顾客回复流、实时风险识别、训练评测。提示词、超时和响应解析由适配层负责，服务层只处理业务输入输出。生产调用失败时保留当前会话及已提交消息，返回可重试错误；不得静默切换 Mock 或保存伪造报告。

## 5. 业务迁移切片

### 阶段 1：工程基础

- 创建前后端应用、配置加载、健康检查、数据库连接、统一异常和请求 ID。
- 建立 `/api/v1`、Axios 客户端、Vue Router、Pinia 和基础页面壳。
- 建立 Alembic、pytest、Vitest 和 Playwright 基线。
- 提供模板风格的安装、启动、停止和构建脚本。

### 阶段 2：身份与个人中心

- 创建 MySQL 用户、角色和飞书身份模型。
- 完成飞书 OAuth、JWT、路由守卫和服务端权限依赖。
- 迁移任务、知识进度和实战覆盖摘要，交付新个人中心框架。

### 阶段 3：知识与题库

- 移植 Markdown、Excel、思维导图解析、规范化、版本、来源和冲突门禁。
- 迁移题库发布、专题抽题、服务端判分、答题记录和覆盖率计算。
- 保持当前正式内容与专题练习行为等价。

### 阶段 4：AI 实战与记录

- 迁移场景目录、场景版本、会话恢复、多轮消息、风险提示和报告 SSE。
- 接入 Ark Provider 并保留确定性 Mock 供测试使用。
- 实现实战记录时间线、状态筛选、同场景折叠、组内分页和移动端布局。

### 阶段 5：管理端与切换

- 迁移知识健康、题目和场景管理、AI 草稿、任务分配、报告复核和管理历史。
- 完成全量迁移演练、生产维护窗口、最终增量迁移、对账和域名切换。
- 观察生产指标并完成旧系统下线条件确认。

每个阶段必须形成可独立运行的纵向闭环并通过对应自动化测试，不能等到最后一次性集成。

## 6. 数据迁移与回滚

- MySQL 使用 `utf8mb4`；业务时间以 UTC 保存，界面转换为 Asia/Shanghai。
- 保留现有 UUID、场景 ID、版本 ID、时间戳、来源定位、消息顺序、报告、分数和审核关系。
- JSON、数组及枚举字段在迁移程序中进行确定性转换，转换规则进入自动化测试。
- 正式切换前至少在隔离 MySQL 数据库完成两次可重复演练。
- 正式维护窗口先阻止旧系统新写入，再导出最后增量、导入、对账并执行代表性页面冒烟。
- 对账包括逐表行数、外键完整性、关键字段哈希、会话消息数、报告数、任务归属和抽样用户聚合结果。
- 任一关键校验失败则不切换入口，保留旧系统并恢复写入；MySQL 失败批次不作为生产权威数据。

## 7. 错误、安全与可观测性

- 每个数据库业务动作使用事务，写入失败不留下部分状态。
- AI 超时、限流、空响应和解析失败使用不同错误码，并记录脱敏日志。
- 所有学员和管理员资源在服务端按当前用户校验，不能仅依赖前端隐藏按钮。
- Cookie、OAuth 状态、JWT 密钥、飞书密钥、Ark 密钥和数据库连接串只来自环境或公司密钥系统。
- 日志包含请求 ID、路由、耗时和结果，不记录 JWT、密钥或完整敏感对话。
- 上线观察认证失败率、API 5xx、数据库连接、Ark 超时和报告 SSE 完成率。

## 8. 测试与验收

### 自动化测试

- pytest：领域服务、权限依赖、SQLAlchemy Repository、API、Ark 失败路径和迁移转换。
- Vitest/Vue Test Utils：Pinia、路由守卫、API 错误映射、时间线分组、折叠和分页。
- Playwright：学员登录与训练、管理员管理、会话恢复、报告生成与失败重试。
- 数据迁移测试：固定旧库样本迁移后比较数量、关联、关键哈希和业务聚合结果。

### 完成标准

- 当前所有学员端和管理端能力在新系统中有等价入口。
- 服务端正确拒绝未登录、角色越权和跨用户资源访问。
- 历史账号、内容、题库、任务、会话、消息、报告和审核记录完整迁移。
- AI 会话可恢复，报告 SSE 失败可重试且不重复生成错误状态。
- 实战记录在移动端以紧凑时间线展示，同场景记录可折叠并分页。
- 公司 Linux 环境可以通过标准脚本安装、启动、停止、构建和回滚。

## 9. 部署与脚本约束

- 开发环境：FastAPI 监听 8005，Vite 监听 8006 并代理 `/api`。
- 生产环境：Nginx 提供 `frontend/dist`，将 `/api` 转发到仅监听本机的 Uvicorn 8005。
- Uvicorn 由 systemd 负责启动、重启、日志和开机运行。
- `start.sh`、`stop.sh`、`install.sh` 和 `build.sh` 遵循公司模板的使用方式。
- `update.sh` 不执行 `git reset --hard`；只允许获取远程后执行可验证的 fast-forward，工作区不干净或分支分叉时立即停止并提示人工处理。

## 10. 范围边界

本次迁移不新增积分、排行榜、正式考试防作弊、开放式 RAG、多模态或与现有训练闭环无关的产品功能。除已确认的实战记录压缩外，界面以功能等价为目标；额外产品重设计必须另立规格。
